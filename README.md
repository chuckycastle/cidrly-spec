# cidrly-spec

The contract every cidrly implementation must satisfy.

cidrly has more than one implementation: the TypeScript CLI
([chuckycastle/cidrly](https://github.com/chuckycastle/cidrly)) and the Swift package behind the
iOS, iPadOS, and macOS apps. This repository is what keeps them in agreement. It holds no engine
code, only the plan file schema, the conformance fixtures that describe the engine's behavior, and
the golden export outputs.

## Contents

```
schema/     JSON Schema for the plan file (.cidrly / .json), one file per schema version
fixtures/   Engine inputs and expected outputs, generated by the CLI's fixture generator
  engine/     sizing, masks, subnet details, containing block, allocation, IPAM-lite, auto-fit, overlap
  rules/      VLAN rules, IP classification
  format/     plan file parsing rules, import round trips
  golden/     text exports of the example plans for every supported format
  manifest.json
docs/       Plan file format and fixture format documentation
```

## How implementations use it

- **CLI (TypeScript).** `.spec-version` in the CLI repo pins a tag of this repository. CI regenerates
  the fixtures from the engine and diffs them against the pinned tag (`npm run conformance`).
- **Apple (Swift).** The `cidrly-apple` repo vendors `fixtures/` at a pinned tag and runs them
  through `CidrlyCore` in its test target (`Scripts/sync-spec.sh`).

## Changing engine behavior

1. Open a PR here with the regenerated fixtures and a CHANGELOG entry that explains the behavior
   change in words. Fixtures are generated, never hand-edited, by:

   ```bash
   # in the cidrly CLI checkout
   npm run fixtures -- ../cidrly-spec/fixtures
   ```

2. Merge and tag (`vMAJOR.MINOR.PATCH`). A change that alters existing expected values is a MINOR
   bump; a change to the plan file schema is a MAJOR bump.
3. Land the implementation PRs in each repo and bump their `.spec-version` pin.

A behavior that exists in only one implementation is a bug, not a feature, until it is here.
